# 存储方案：GitHub 放多少、放什么、超了怎么办

你问的核心是"整体照片要求保存在 GitHub 仓库内（如果 GitHub 没有存储上限的话）"。
结论先说：**GitHub 有上限，而且对照片来说很容易撞上**。
所以推荐的做法是"**缩略图/预览图进仓库，原图按需处置**"。

---

## 1. GitHub 的实际限制（2025 年现状）

| 限制 | 数值 | 影响 |
| --- | --- | --- |
| 单个文件大小 | **100 MiB 是硬上限**（超过直接拒绝 push）；>50 MiB 会警告 | 你的原图一般 5~30 MB，不撞这条 |
| 仓库体积 | **强烈建议 < 5 GB**（官方"recommended limit"，超过可能被联系要求瘦身） | 这是主要天花板 |
| GitHub Pages 站点大小 | **≤ 1 GB**（发布的站点产物） | 相册站点真正能用的容量 |
| GitHub Pages 带宽 | 每月 **100 GB 软上限** | 一天几百人访问没问题 |
| Git LFS 免费额度 | 免费账号有一份小额存储与月流量额度，超出后按量计费（可把预算设成 $0，则当月被限流） | 见下方说明 |
| Pages 构建 | 10 分钟超时；软限每小时 10 次构建 | 相册几百 MB 没问题 |

依据（官方文档）：
[仓库限制](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)、
[关于大文件](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)、
[GitHub Pages 限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)、
[Git LFS 计费](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)。

### 那"能不能全部塞进去"？

能，但要看照片数量和大小。本工具生成的两类文件体积差别很大：

| 文件 | 典型大小 | 说明 |
| --- | --- | --- |
| 原图（相机 JPEG） | 4~10 MB | 24MP 相机 JPEG |
| 原图（Lightroom 导出 JPEG） | 3~8 MB | 质量 80~90 |
| 预览图 `media/previews/*.webp` | ~200~500 KB | 1600px，长边 |
| 缩略图 `media/thumbs/*.webp` | ~30~60 KB | 400px，长边 |

按"预览 + 缩略图"算，每张约 **0.3 MB**：

| 照片数量 | 仅缩略图+预览 | 加上原图 |
| --- | --- | --- |
| 1,000 张 | ~300 MB | ~7 GB ❌ 超限 |
| 3,000 张 | ~900 MB | ~21 GB ❌ |
| 5,000 张 | ~1.5 GB ⚠️ 接近 Pages 1 GB | ~35 GB ❌ |
| 10,000 张 | ~3 GB ❌ 需换方案 | ❌ |

**所以：仓库里放"预览图 + 缩略图"是可行的（几千张以内），放原图基本不可行。**

## 2. 推荐：分层存放（默认策略）

```
原图（RAW + 精修 PSD/TIFF + 原始 JPEG）
   └─ 留在本地硬盘 / NAS / 移动硬盘 / 网盘，不进仓库

仓库（GitHub）
   ├─ public/data/*.json     索引：日期、地点、参数（几十 KB ~ 几 MB）
   ├─ public/media/thumbs    400px WebP 缩略图
   ├─ public/media/previews  1600px WebP 预览图
   └─ public/media/originals ← 只有你显式 --copy 才会有
```

对应命令：

```powershell
# 默认：不复制原图，只生成缩略图与预览（推荐）
npm run import -- --src "D:\照片归档"
```

> 网页导入同理：在「导入」页选 **轻量** 就是这一档；选 **完整** 相当于加了 `--copy`。
> 网页里也可以只改一张的地点/日期（点「修正」），敏感位置不需要动原文件。

灯箱里"预览图"就是 1600px 的 WebP，屏幕上看着和原图几乎一样。
如果某张想给原图下载链接，可以单独把这一张丢进 `public/media/originals/`。

### 为什么不用 Git LFS 装原图？

Git LFS 能绕过 100 MiB 单文件限制，但：

* 免费额度很小（存储 + 每月流量），照片库几乎必然超出；
* 超了以后要么当月被限流，要么开始计费（[LFS 计费说明](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)）；
* **GitHub Pages 不通过 LFS 提供文件**——也就是说 Pages 站点里用不了 LFS 里的照片；
* 克隆仓库的人会被迫下载全部大文件。

结论：LFS 适合"偶尔几个大文件"（比如一段 4K 视频），不适合"整个照片库"。

## 3. 想要"原图也在云上"的替代方案

### 方案 A：只把预览图放仓库（最简单，推荐起步）

* 仓库：~0.3 MB/张，3000 张以内都很舒服。
* 原图：本地硬盘 + 一份异地备份（移动硬盘 / 网盘 / 时间机器）。
* 站点功能完整（浏览、地图、筛选、统计），只是"下载原图"没有。

### 方案 B：原图放对象存储，站点只存预览图

把原图传到对象存储，导入时用 `--origin-base` 指向它，索引里的 `src` 会自动拼成
`<你的前缀>/<相对路径>`，灯箱里的"下载原图 / 新窗口打开"就能用：

```powershell
# 例：把照片按相同目录结构传到 https://cdn.example.com/photos/ 下
npm run import -- --src "D:\照片归档" --origin-base "https://cdn.example.com/photos"
```

（也可以写在 `photojournal.config.json` 的 `originBase` 字段里。）

可选服务：

| 服务 | 免费/价格 | 备注 |
| --- | --- | --- |
| **Cloudflare R2** | 10 GB 存储免费，**出流量免费** | 目前最划算的图片托管选择 |
| Backblaze B2 | 10 GB 免费，配 Cloudflare 免流量费 | |
| 阿里云 OSS / 腾讯云 COS | 有免费额度，按量计费 | 国内访问快 |
| 七牛云 / 又拍云 | 有免费额度 | 国内图床老牌 |
| 自建 NAS + 内网穿透 | 一次性成本 | 完全自主 |

### 方案 C：拆分多个仓库

GitHub 的 5 GB 是按**仓库**算的。可以按年份拆：
`photos-2023`、`photos-2024`…每个仓库都可以有自己的 Pages 站点。
缺点是管理麻烦，站点之间互相跳转要自己处理。

### 方案 D：不用 GitHub Pages，换静态托管

仓库仍然放 GitHub（只放代码和索引，甚至不放照片），站点发布到：

* **Cloudflare Pages**：免费、无限带宽，直接连 GitHub 仓库自动构建，比 Pages 更宽松；
* **Vercel / Netlify**：同样免费额度，适合个人站点；
* **对象存储 + CDN**：R2/OSS 直接当静态站点用。

这几种都能绕开 Pages 的 1 GB 站点上限；限制就只剩"仓库 5 GB"了。

### 方案 E：图片压缩到极致

* 降低 `media.js` 里的 `previewWidth`（例如 1280）与 WebP 质量（例如 72）；
* 只在仓库里放缩略图（`--no-previews`），灯箱直接看原图（原图放本地/对象存储）；
* 用 AVIF 代替 WebP（同画质再省 ~20%，但 sharp 需要带 AVIF 支持）。

## 4. 体积速查

导入完成后，工具会打印 `media 目录体积`。你也可以随时自己算：

```powershell
# 站点数据总大小
(Get-ChildItem public -Recurse -File | Measure-Object Length -Sum).Sum / 1MB

# 各类文件分别多大
Get-ChildItem public\media -Recurse -File | Group-Object Extension |
  Select-Object Name, Count, @{n='MB';e={[math]::Round(($_.Group | Measure-Object Length -Sum).Sum/1MB,1)}}
```

**红线**：`public/` 总大小保持在 **1 GB 以内**（Pages 上限），
仓库总量保持在 **5 GB 以内**（GitHub 建议上限）。
到 800 MB 左右就该考虑换方案 D 或方案 A 了。

---

## 5. 一句话总结

* **能放 GitHub，但只放"预览图 + 缩略图"，不要放原图。**
* 大约 **每张 0.3 MB**，所以 **3000 张以内** 用 GitHub Pages 完全够用。
* 超过就把原图放对象存储（R2 最省），或把站点搬到 Cloudflare Pages（无限带宽）。
* Git LFS 不是照片库的解法，只适合零星大文件。
