时空立方体 (Space-Time Cube)

把一组照片按拍摄先后沿时间轴堆叠成一个三维立方体：每张照片是 xoz 平面上的一个切片， y 轴就是时间。照片半透明叠加之后，画面里移动的高对比物体（人、车、亮色物）会在时间 轴上连成一条斜线 —— 那就是它的运动轨迹，斜线的倾斜程度就是速度。

正面是第一帧，背面是最后一帧，四个侧面是沿时间方向拉长的颜色条。

怎么打开

浏览器出于安全策略，禁止 file:// 页面把本地图片读进 canvas，所以**直接双击 index.html 会白屏**。用下面任一方式起一个本地静态服务即可：

方式操作
最简单双击 启动.bat —— 自动探测 Node 或 Python，起服务并打开浏览器
想手动停服务powershell -ExecutionPolicy Bypass -File .\启动.ps1 —— 按回车即停
手动node server.js 8730，然后打开 http://127.0.0.1:8730/
VS Code右键 index.html → Open with Live Server

启动.bat 会在后台开一个最小化窗口（标题 spacetime-cube server）来跑服务， 关掉那个窗口就停服务了。不想留窗口的话，用 启动.ps1。

首次打开需要联网（Three.js 从 jsDelivr CDN 加载，已在 index.html 的 importmap 里固定版本）。

浏览器要求 WebGL2（Chrome / Edge / Firefox 近几年版本都支持）。

启动.bat 刻意只写英文 ASCII。cmd.exe 是按系统 ANSI 码页逐字节解析 .bat 的， 里面有中文就会解码错乱、把行结构撑坏，于是出现 'Net.Sockets.TcpClient' 不是内部或外部命令 这类报错。改动这个文件时请保持 ASCII。

用法

  • 打开照片：点左上角「打开照片」，或把一批图片直接拖进窗口。支持 JPG / PNG / WebP / BMP / GIF。
  • 排序：右上角切「按文件名」或「按修改时间」，决定谁在前谁在后。
  • 旋转：按住拖动即可环绕观察；滚轮缩放；双击或按 R 复位。

里面没有帧滑块 —— 因为所有帧都同时显示、且各自待在自己的时间位置上， 「选择某一帧」这件事在语义上已经没有意义了。

两种模式

模式行为
全不透明所有帧都按 1.0 参与 → 一个实心的彩色立方体。正面就是第一帧，转到侧面能读到沿时间拉长的颜色条。
全半透明所有帧按「轨迹强度」参与 → 轨迹从背景里浮出来。这是默认模式。

两种模式唯一的差别就是「轨迹强度」这一个参数，没有别的隐藏差异。

为什么用「取最大值」而不是叠加

这是整个项目最关键的一个决定，也是前面几轮画面一直糊的根本原因。

直觉上「把照片半透明叠起来」就是求和，但那在几百帧时必然糊： 每一帧都往同一个像素上叠一点，静态内容立刻饱和成一片灰白，动态内容只剩一级级的台阶 —— 看起来像城墙的垛口，曝光一变台阶更明显。

正确的合并算子是取最大值（MIP, Maximum Intensity Projection）： 每个像素取的是「它在整段时间里最亮的样子」。亮度不累积，所以永远不会糊、 不会发白，颜色也永远不会溢出立方体。

所有帧都在自己的时间位置上

没有任何一帧被特殊对待 —— 包括「当前帧」。它就在它该在的那一层， 和其他帧完全平等地被 MIP 合并。

（早先的版本把选定帧强行提到最前并单独提亮，结果它看起来"飘"在立方体外面。）

三个滑块

滑块含义建议
轨迹强度轨迹的不透明度倍率，0 ~ 3。因为轨迹是「取最大值」合并的，它的浓淡不由帧数决定，而是由这个滑块决定。调到 1 以上轨迹就接近完全实心。0.8 ~ 1.5。太淡就往上调。
背景抑制亮度低于此值的像素直接抠掉（alpha 归零），它们不会进入立方体。背景杂乱时试 0.2 ~ 0.5。背景干净时留 0。
画质渲染分辨率相对画布的比例。调高会超采样（更锐利但更慢）；帧数多时会被自适应压到 1 以下以防 GPU 卡死，状态栏会显示实际渲染分辨率。卡就往下调；想更锐就往上调。

几个实际会遇到的问题

为什么侧面看到的颜色条会被拉长、还有点糊？ 因为深度方向就是时间。相邻两帧之间是线性插值的，所以时间上渐变的东西会显得柔和。

会不会有「城墙一样一级级的凸起」？ 那是求和式叠加的典型症状：几百帧各叠一点，静态内容饱和成灰白，动态内容只剩台阶， 曝光突变时更明显。现在的轨迹用「取最大值」合并，再加上相邻帧的时间插值填缝， 不会出现这种现象。如果你还看到台阶，把「背景抑制」调高一些 —— 背景没被抠干净时， 它的空隙会把台阶托出来。

背景抑制调高之后，轨迹反而变干净了？ 对。背景如果一直在动（比如树叶、人群），它会在时间轴上累积成雾。抑制阈值把暗部清掉之后， 只有真正高对比的目标会留下轨迹。这是让效果接近参考视频的关键一步。

照片很多会卡吗？ 内部会把单帧降采样到长边 1024 像素以内（只降不升），并控制整块 3D 纹理的体素总量 （约 2.6 亿体素，对应约 1 GB 显存）。最多保留 512 帧，超出会等间隔抽稀。

为什么状态栏显示的渲染分辨率比窗口小？ 因为采样代价 ≈ 像素数 × 帧数。几百帧的时候逐像素做几百次取样会把 GPU 拖死， 所以渲染分辨率会被自适应压低，再由浏览器放大显示。这比掉到几帧每秒要好用。 把「画质」滑块调高可以超采样，但自适应只会往下压，不会超过滑块给的上限。

照片长宽比不一样会怎样？ 以第一张的长宽比为准统一缩放，其余照片会被拉伸到同一尺寸。同一批照片建议保持同样比例。

画面里的照片会不会被裁掉？ 不会。fit.js 专门负责这件事：视锥取 halfY = max(体数据半高, 体数据半宽/画布宽高比)， 既保证立方体在水平和竖直方向都完整进画面，又保证 halfX / halfY 恰好等于画布宽高比 （像素不变形）。自检里用 6 种屏幕比例（16:9 / 1:1 / 9:16 / 4:3 / 21:9 / 1:3）逐一验证过。

自检

核心渲染数学、着色器静态正确性、启动脚本都有不依赖浏览器的断言：

node test/selftest.js                          # 渲染数学与数据布局（13 项）
node --experimental-vm-modules tools/syntax-check.js   # 语法（10 个文件）
node tools/glsl-audit.js                       # GLSL 静态审查（13 项）
node tools/smoke.js                            # 端到端：资源、依赖、uniform 一致性（15 项）
node tools/check-launcher.js                   # 启动脚本编码与 Python 回退（12 项）

test/selftest.js 在 Node 里复现了着色器的切片路径，并断言：

  • 体素下标编解码与 THREE.Data3DTexture 的约定一致（v 对应时间轴，v=0 是第一帧）
  • 全不透明模式下，正视时取到的就是第 0 帧的像素（这就是「正面是第一帧」）
  • 有运动的位置出现轨迹；无运动处保持为纯背景（MIP 不累积底噪）
  • 输出不超过该处最强的单帧（这就是它不糊、颜色不溢出立方体的原因）
  • 边界夹紧：任何采样点的纹理坐标都落在 [0,1] 内
  • 像素 → 体坐标 → 体素 的往返恒等
  • 背景抑制确实把暗背景的 alpha 清成 0 而保留亮部

tools/glsl-audit.js 在拿不到 GPU 编译器的情况下，尽量把「编译期就能发现的错误」查出来： 未声明的标识符、只赋值不声明的变量、括号配平、uniform 双向一致性， 以及 swizzle 分量越界（.a 不能用在 vec3 上 —— 这类错误会直接让整个着色器编译失败， 画面全空而 JS 一切正常，从外部完全看不出来）。

这类静态检查的难点是假阴性：第一版 swizzle 检查把 swizzle 剥掉之后才去验证它， 等于验了空集，明明有 bug 却报通过。所以新增检查时必须故意把 bug 注回去、确认它真的会报错。

浏览器里的视觉确认请直接打开 启动.bat。仓库里的 test/ 是一个可以用 URL 参数 固定状态的调试页（?mode=ghost&slice=12&phi=-38&theta=22），配合 http://127.0.0.1:8730/test/ 使用。

出问题时：页面会自己把着色器编译日志、运行时错误直接显示在画面上， 不用去翻 F12 控制台。如果你看到红字，把它发出来即可。

实现要点

为什么是体渲染而不是「堆一堆半透明图片」？ 其实两者等价，但用一张 3D 纹理 + 一条射线更省：几千张图片是几千次 draw call， 而这里永远只有一次；而且采样步长可以随帧数自适应，帧数从 10 涨到 500 都不需要改代码。 半透明帧用加性混合，天然与顺序无关，不会出现「谁挡住谁」的排序伪影。

相机为什么用正交投影？ 你要求「正对立方体、无透视拉伸」。正交投影下各面都是严格的矩形，切片的几何就是 真正的 xoz 平面，跟一开始的心智模型完全一致。

视锥是按体数据尺寸算的，不是固定视锥角。 这点很关键：照片平面的高度是 照片高/帧数，帧数一多它就会缩得很小。 如果沿用固定视锥角，立方体上下会被裁掉。所以 layout() 先让平面铺满画面高度， 再按窗口宽高比撑开宽度，保证像素不变形。

帧上传是「最旧优先」的队列。 GPU 上第 y 帧与第 y+1 帧相邻，顺序推进 texSubImage3D 会形成一条连续的上传带， 比随机顺序快得多。
