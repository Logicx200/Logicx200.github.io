# 时空立方体 · 三维查看器（v2）

把一组照片（或一段视频抽出来的帧）按时间先后沿**时间轴**堆成一个真正的三维立方体，可以在里面转着看。

- **正面 = 第一帧，背面 = 最后一帧**，四个侧面 = 边界像素沿时间轴拉成的颜色条。
- **照片和视频都可以拖进来**：视频会先被抽成一串帧，再与照片一起堆叠；
  **默认每一帧都保留**，绝不替你抽稀（要抽稀得自己在下拉里选）。
- 每张照片是一个**有厚度的薄片**（厚度可调），所以正视图里侧面也不会退化成一条零宽的线；
  帧间距可调，薄片永远不会互相穿模。
- 帧滑块选一帧作为当前帧，其余帧以可调不透明度半透明显示，也可以显示成**点云**；
  点云密度按亮度加权，**亮处更密 / 暗处更密**都可以选。
- 照片按**原画质**解码与上传，不做任何缩放、重采样或有损压缩。

**零依赖、零构建、完全离线**：整个程序就是一个 `index.html`，双击用浏览器打开即可，
不联网、不需要本地服务、不需要 CDN。

> 与上一版（`../` 目录）的区别：上一版把时间放在 **y 轴**（垂直堆叠）、用 3D 纹理体渲染、
> 且会**把每帧降采样到长边 1536**；这一版时间在 **z 轴**（前后堆叠，正/背面正好是首末帧）、
> 逐帧独立贴图、**不降分辨率**，并且多了帧滑块、点云模式与侧面颜色条。
> 上一版的文件原样保留在 `../`，没有改动。

## 怎么打开

直接双击 `index.html`（或用浏览器拖进去）。

建议用较新的 Chrome / Edge / Firefox，需要 **WebGL2** 与联网**无关**。

### 如果双击打开后是白屏或报错

浏览器在 `file://` 下会禁止页面读回 canvas 像素，而这个程序有两处**必须**读像素
（生成侧面颜色条、构建点云颜色）。遇到这种情况会弹红字提示，按提示用本地服务打开即可：

```
node tools/serve.mjs 8731
```

然后访问 <http://127.0.0.1:8731/>。`tools/serve.mjs` 只用 Node 内置模块，不装任何东西。

> 想快速看效果，可以用仓库里的合成样本（24 帧、320×240、无损 PNG）：
> <http://127.0.0.1:8731/index.html?demo=./sample/frame_%03d.png&n=24>

## 几何模型

```
      +X  画面向右
      +Y  画面向上
      +Z  从第一帧指向最后一帧 —— 也就是时间轴的正方向
```

- 每张照片是 `xoz` 平面上的一个二维切片，宽固定为 1，高按原始长宽比；
- 第 i 帧摆在 `z = i · depth/(n−1)`，于是**第一帧在 z = 0、最后一帧在 z = depth**；
- 每帧还沿 z 方向**挤出一点厚度**（默认 0.02，即照片宽度的 2%），变成一个薄片：
  - **照片本身在薄片的中面**上，薄片占 `[z−d/2, z+d/2]`；
  - 厚度会被自动夹到**帧间距的 90%**，所以帧距再小也不会互相穿模；
  - 面板里显示成 `0.020（≈60 px · 帧距的 14%）` —— 后两个数字分别是
    "换算成原图多少像素"和"占帧间距的比例（被夹住时会写明）"；
- **四个侧面就是每张薄片的四个立面**：左/右立面 = 该帧原图最左/最右一列，
  上/下立面 = 最上/最下一行。所以斜着看，每张照片都有一圈属于它自己的真实颜色边。

**从哪个视角能看到哪几个立面**（这一段很重要，它是"为什么只看见上面"的答案）：

| 视角 | 能看到的立面 |
| --- | --- |
| **正视** | **一个都看不到**。四个立面全都正对着相机、屏幕投影退化成一条零宽的线。这不是 bug：一块垂直于视线的薄板，本来就看不到它的边。 |
| **等轴**（默认） | 上（或下）+ 左（或右）两个。剩下两个背对相机，被立方体自己挡住 —— 也是正确的遮挡关系。 |
| **俯视** | 只有上、下两个。左右两个退化成线。 |

也就是说，**任何单个视角最多只能看到四个立面里的两个**。要确认四个面都画出来了，
用面板里的「**诊断：四色立面**」（左红 / 右绿 / 上蓝 / 下黄）——
把颜色换掉之后，就与"照片自己的边缘是深色还是浅色"无关了。CLI 上等价于 `?banddebug=1`。

> **另一个容易误判的地方**：立面的颜色就是**你自己照片的边缘颜色**。
> 一张典型风景照，上边是天空（亮），左右和下面是地面/暗部（暗）。
> 深色立面压在深色背景上（画布底色是 `rgb(5,7,10)` 那种近乎黑）就会看不见，
> 看起来就像"只有上表面生成了"。这时候把「帧厚度」调大一点、
> 或者打开四色诊断，就能立刻分辨"没画出来"和"画出来了但颜色跟背景一样"。

**厚度条的不透明度跟着那一帧照片走**：把「其他帧」拉到 12%，它们的边也一起淡到 12%；
拉到 0 就整个消失。不透明的边写深度，半透明的边由远到近画、不写深度 ——
与帧平面完全同一套规则。

**开关**：面板上的「显示厚度条」可以整体关掉（关掉时会连那四张图集纹理一起释放）。

**侧面颜色条有两种取法**（控制面板可切）：

| 模式 | 含义 |
| --- | --- |
| **边界像素**（默认） | 立面就是那一帧原图最外一列/一行，取的是**真实 RGB**。 |
| **整行/整列平均色** | 每条边压成一个均值（每条边只有 1 列，省显存）。 |

**帧间距**（`帧间距` 滑块，0.2 ~ 6）就是立方体沿时间轴的深度 `depth`：调大则帧之间离得远、
轨迹被拉得更长，调小则帧挤在一起。它只重排几何、**不重新解码**，所以拖动是即时的。
默认 1.6（= 照片宽度的 1.6 倍）。

## 视频：抽帧，而且每一帧都保留

把 mp4 / mov / webm 拖进来（或点「打开照片/视频」）就能用。视频先被抽成一串帧，之后
**与照片完全同等对待** —— 滑块、半透明、厚度条、点云、导出 PNG 全都一样。

### 怎么抽的（以及为什么这么做）

**逐帧播放，每呈现一帧就抓一帧。** 判断"这一帧"的唯一可靠依据是浏览器解码器
**实际呈现过**的帧，而那正好就是 `requestVideoFrameCallback` 的回调。

- 不用"按固定时间间隔 seek 抽帧"：seek 只能落到关键帧附近再解码，抽出来的时间点
  既不均匀也不等于真实帧时刻，而且更慢。
- 当前帧的时间戳（`mediaTime`）会记在每一帧上，所以"有没有跳帧"是可核对的：
  正常应该是首帧 0 秒、之后每 1/fps 递增一格。

#### ⚠️ 这里有一个必须讲清楚的坑（真实故障，已修）

把视频帧搬进内存要**一次拷贝**（`createImageBitmap`），4K 一帧就是 30 MB 量级。
第一版在回调里 `await` 拷贝完**才登记下一帧的回调** —— 那等于每帧都把整条回调链
卡住几十毫秒，浏览器于是把"来不及呈现"的帧通通丢掉。用户实测：

```
DSC05088.mp4：解码器报了 233 个丢帧（呈现 92 帧、保留 92 帧）
```

300 多帧的视频只留下 92 帧，**丢了 70%**。所以现在的做法是两条：

1. **回调链永不被我们的处理阻塞**：进回调就先登记下一帧的回调，
   拷贝异步排队（多画布轮转，保证快照不会互相覆盖）；
2. **背压**：积压到一定程度就**降低播放速度**（`playbackRate` 0.25 → 0.0625），
   快用满画布池就**暂停播放**，等拷贝追上来再继续。解码器于是不再丢帧 ——
   代价是总耗时可能超过视频时长，但**一帧不少**。

抽帧时会顺手探一下能不能**直接从 `<video>` 取快照并缩放**
（`createImageBitmap(video, {resizeWidth…})`，Chrome 支持）：能的话就省掉
整帧的 canvas 拷贝 —— 这是吞吐量最大的一项优化。少数浏览器不支持，会自动退回 canvas 路径。

进度条上会显示「已抓 N 帧（呈现 M 帧）　X 帧/秒　约还需 Y 秒」，
跟不上时还会写明「跟不上，已降到 0.25× 速度（保帧优先）」——
**慢是可以接受的，丢帧不行。**

| 控件 | 说明 |
| --- | --- |
| **视频：每帧保留**（默认） | 每一帧都进立方体。 |
| **每 2 / 3 / 5 帧取 1** | 只有你显式选了才会抽稀。**用它来"解决丢帧"是错的** —— 那只是少抽样，不是把丢掉的那几帧找回来。 |
| **分辨率**（顶栏） | 与照片同一套策略。**只有选「自动适配」时**程序才会先花约 2 秒探测帧率、估算总帧数，再按 `n × 宽 × 高 × 4 ≤ 预算` 解出长边 —— 这样"全部帧都装得下"是算出来的，不是猜的。 |
| **取消**（进度条上的按钮） | 长视频可以中途停下。 |

### 老实说的三条边界

1. **抽帧速度取决于拷贝速度，不一定实时。** 机器越快越接近实时；拷贝跟不上时会自动
   降到 0.25× 甚至暂停（保帧优先），进度里会写清楚当前倍速。
2. **解码器会不会丢帧，我们说了不算，但会报出来。** 即使已经降速，如果 `droppedVideoFrames`
   仍然不为零，说明这台机器在该分辨率下确实搬不动 —— 提示会直接建议**调低分辨率**，
   而不是建议抽稀。
3. **两个硬上限**：帧数上限 2000 帧、以及显存预算。够到任何一个都会**停下来并报出**
   "估计共 N 帧，本次只保留前 M 帧"，同时给出出路（更低分辨率，或在帧数上限那种情况下
   "该每几帧取 1"）。程序不会替你丢帧，也不会背着你压缩。

> 没有 `requestVideoFrameCallback` 的浏览器（较老的 Firefox）会退化成 rAF 采样：
> 只在 `currentTime` 真的变化时抓一帧，避免重复帧，但帧数可能与真实帧数有出入 ——
> 这一点会在提示里写出来。

### 提示条：3 秒后自己渐隐

丢帧在抢占式系统里**无法完全避免**（别的进程占着 CPU/GPU 时解码器就是来不及呈现），
所以红色的提示条不该变成一个需要用户每次手动去关的东西 —— 那最后就变成"永远有一块红字
挡着画面"。现在的行为是：

- 载入后显示 **3 秒** → `opacity` 用 0.9 秒过渡**渐隐**到 0 → 不再占位（`pointer-events: none`）；
- **点一下它**就再看 3 秒（完整文本同时留在 `title` 里，鼠标悬停也能看到）；
- **换一批照片/视频时旧提示立刻被清掉**，不会带着上一批的警告。

提示的语气也按丢帧比例分档：**≤ 5%** 只说一句"属于正常抖动，可以忽略"；
更高时给出具体比例并建议**调低分辨率**（而不是抽稀）。

### 与照片混在一起时怎么排序

视频的帧**作为一个连续的块**参与排序（块内严格按时间顺序），块的排序键用视频文件自己的
文件名 / 修改时间；`按拍摄时间（EXIF）` 模式下视频没有拍摄时间，会排在有时刻的照片之后。
注意：**长宽比与其它帧差太多的视频/照片会被拉伸**（所有帧共用同一个平面尺寸），
所以混排时最好用同一种画幅。

## 投影：正交，不是透视

**相机一律用正交投影**，没有近大远小。

理由很具体：这个工具是用来**读图**的。透视会让远处的帧变小，于是同一段位移在不同
深度上量出来的像素长度不一样，帧与帧之间失去可比性，轨迹的"斜率"也被距离污染。
正交下立方体的每个面都是严格的矩形，切片的几何就是真正的 `xoz` 平面 ——
与"照片是二维平面、沿 y 轴按时间排列"这个心智模型完全一致。

### 尺度恒定：转动视角时大小不变

**取景范围按包围球定死，不随视角变化。** 这一条是刻意的：

早先是按「旋转后的包围盒」拟合视锥，于是立方体转到对角线时投影范围最大、
正对时最小，**两者相差 √3 ≈ 1.73 倍** —— 转起来就是忽大忽小，很难受。
包围球半径与旋转无关，所以改成 `halfH = 半径 × 1.16` 之后，尺度就是一个常数。

自检里把这条钉死了（120 多个视角）：

```
全部 97 个视角下视野半高都是同一个常数  — 半高 = 1.177628549（121 个视角全部相同）
绕方位角旋转时竖直尺度完全不变（不会忽大忽小）  — 竖直像素/单位 ∈ [339.665675, 339.665675]
换算成「世界单位/像素」在各方位角下是同一个常数  — 世界单位/像素 = 0.002944071
窗口 1600×500 / 500×1200 / 900×900 下竖直尺度与 1200×800 一致（只与 zoom 有关）
```

也就是说：**缩放只由滚轮（zoom）控制，与视角、与窗口形状都无关。**
代价是正对时四周会多留一些空 —— 这是"不缩放"必须付出的，也正是想要的效果。

## 功能

### 时间轴

| 控件 | 作用 |
| --- | --- |
| **当前帧滑块** | 选择哪一帧是"当前帧"。它在自己的时间位置上按"当前帧不透明度"显示。 |
| **全部半透明** | 取消当前帧的特殊地位，所有帧用同一个不透明度。 |

当前帧的位置**不会**被挪到最前——它就在它该在的那一层。所以转动立方体时，
你能看到它在时间轴上的真实位置。

### 不透明度

| 控件 | 范围 | 说明 |
| --- | --- | --- |
| **当前帧** | 0 ~ 1 | 1.0 = 完全不透明（默认）。 |
| **其他帧** | 0 ~ 1 | 0 = 完全透明。这一帧连**侧墙一起**消失 —— "完全透明"就该真的看不见。立方体线框与时间轴不受影响，空间结构不会丢。 |

**"全部不透明"（两个都拉到 1.0）就是实心立方体**：正面是第一帧、背面是最后一帧，
四个侧面是颜色条。这正是默认形态之外的另一种看完整立方体的方式。

### 其他帧的显示方式

- **半透明平面**（默认）：每帧一张贴图平面，按不透明度混合。
- **点云**：非当前帧的每个采样像素变成一个屏幕对齐的小方块（两个三角形），颜色取自原图。
  - 密度由"总点数预算"（400 万点）自动决定，状态栏会显示实际点数；
  - **1 像素 = 1 个点**时步长为 1，颜色就是那个像素的原始字节，不做加权平均；
  - `点大小`：单位是**屏幕像素**，与视角、与照片分辨率都无关；
  - `方格点` 开关：开启时每个点严格等于一个原始像素（不羽化、不插值）；
    关闭时画成圆点，观感更柔和但边缘有抗锯齿过渡。

#### 点云密度按亮度加权

这是"点云"这一模式真正有意思的地方：**不是均匀撒点，而是按画面的明暗决定密度。**

| 控件 | 说明 |
| --- | --- |
| **亮处更密 / 暗处更密** | 密度正比于哪个方向的量。两者互为镜像，同一张图选哪个取决于你想看什么（高光轮廓还是暗部结构）。 |
| **密度幂次** | `密度 ∝ 量的^幂次`。1.0 = 严格正比；调小则"稀疏的那一头"也保留更多点。 |
| **门槛** | 参与密度的量低于它时**一个点都不画**。 |

实现上没有额外的显存开销：每个像素用坐标算一个稳定的伪随机阈值
（`h = fract(sin(dot(px, (127.1,311.7))) · 43758.5453123)`），
阈值在 `[0,1)` 上均匀分布，于是"保留"的概率正好等于密度量本身。
用哈希而不是随机数，是为了让**同一个像素每帧都得到同样的结果**（不会闪）。

> 点云是**屏幕对齐的方点**，靠顶点着色器把 `aPos`（单位方块四角）在裁剪空间里撑开：
> `clip.xy += aPos.xy · 0.5 · size · (2/viewport) · clip.w`。
> 这里**不能用 `gl_PointSize`** —— 那只在 `gl.POINTS` 下有效，而我们画的是三角形。
> 见下面 10 号 bug。

### 轮廓提取：只保留对比鲜明的颜色分界线

面板里的「**只保留轮廓（颜色分界线）**」（默认关闭）+「**对比门槛**」滑块（默认 0.25）。

打开后，每张照片里**平坦的区域被整片丢掉**，只留下颜色发生突变的那些线。它是在
**照片自己的纹理上**做的（不是屏幕空间后期），所以轮廓跟着照片一起贴在它那一层上，
转动立方体时和照片严丝合缝。

判据是**逐通道最大差**，不是亮度差：

```
m = max( |Δr|, |Δg|, |Δb| )   // 与上下左右四个邻居各算一次，取最大
m ≥ 门槛  →  留下（颜色往白里提 60%）；否则 discard
```

为什么不用亮度差：红↔绿这种**亮度几乎相同**的强对比（Rec.601 亮度都是 0.299）
亮度差接近 0，会被整片漏掉 —— 而那恰恰是"颜色分界线"最典型的例子。
这条在自检里被单独钉住（`outlineContrast` 对红/绿边界的返回值是 1.000）。

采样步长取 `max(fwidth(uv), 一个纹素)`：

- `fwidth` 让线宽始终约等于**一个屏幕像素** —— 照片缩小显示时线不会细到看不见；
- 下限取一个纹素，保证不会在同一个纹素内部取样 —— 照片放大到 1 纹素以上时不会整片变噪声。

几点预期行为（不是 bug）：

- 门槛调高 → 只留最"硬"的边界，弱边界先消失；
- 细小的东西（一根 2 像素宽的线）**整根都会被判成边界**，因为它的每个像素都在采样步长之内；
- 内部是 `discard` 而不是"画成透明" —— 这样不会在深度/混合上留下残影；
- 它是开关，不是破坏性处理：关掉立刻回到完整照片。

### 切割：只显示某一块区域内的影像

面板里的「**切割**」：一个开关 + 「框选区域…」+「整个画面」。

点「框选区域…」会在**当前帧**的照片上打开一个框选面板：

- 在图上**按住拖动** = 画一个新矩形；
- 拖矩形**内部** = 整块移动；
- 拖**四角/四边** = 缩放；
- 选区外自动压暗（那就是会被丢掉的画面）；「整个画面」复位、「取消」放弃这次框选（Esc 也一样）。

**选区是按图像坐标（归一化 uv）存的，所以它对所有帧生效** —— 200 张照片会被切出同一块区域，
而不是只切当前那一张。实现上它发生在片元着色器里（选区外的片元直接 `discard`），
照片本身没有被修改，关掉开关立刻恢复完整画面。

几个要点：

- **判据含边界**，且与 CPU 侧 `STC.view.clipContains` 是同一套：`u ≥ x0 && u ≤ x1 && v ≥ y0 && v ≤ y1`；
- **v = 0 是图像顶部**（与像素编辑器一致，与帧平面的 uv 一致），所以框选面板里看到的上下
  就是 3D 里看到的上下，不会镜像；
- **点云也吃这套选区**：`POINT_VS` 里有同一条判据，否则切到点云模式选区就失效了；
- 选区小到不足 1 像素时会被撑到 1 像素 —— 避免出现"整幅都看不见"这种看起来像故障的状态；
- 选区是「整个画面」时复选框会被置灰：勾上也没有任何效果，置灰比"勾了却没变化"诚实；
- **叠加**：切割与轮廓提取可以同时开（先切、再在留下来的部分里提轮廓）；
- **侧面厚度条不参与切割**：它是薄片的外壳（照片最外一列/一行的颜色），
  跟"选区内的影像"不是一回事。开着「每张照片的显示区域描边」时，那个白框会**跟着选区走**，
  所以它能如实表示"这一帧真正画出来的面积"。

### 标记

- **立方体线框（12 条棱）**：默认打开，**白色**。这是**立方体本身**的框，不是每张照片的显示区域。
- **时间轴**：从第一帧中心指向最后一帧中心的**橙色箭头**（`时间轴` 复选框可以关掉）。
  起点是**第一帧**（正面），箭头指的那一端是**最后一帧**（背面）—— 它表达的是
  "时间往哪边走"，不是"哪边是正面"。早先它两端一样、又因为标记不被遮挡，
  容易被误读成"一根指着正面的黄线"，所以现在加了箭头。
- **每张照片的显示区域描边**：默认**关闭**。打开后每一帧描一圈白色矩形线框
  （`GL_LINES`，当前帧更亮：0.98 vs 0.45）。
  帧数一多（比如 200 张）这些框会叠起来糊成一片白，所以默认关掉。见下面 9 号 bug。

**标记一律画在最上层**：画它们之前会临时关掉深度测试，否则外框会被立方体自己的不透明面
挡住 —— 用户看到的就是"线框没画出来"。见下面 12 号 bug。

## 分辨率与纹理预算：一条绕不过去的算术

**每帧纹理字节 = 宽 × 高 × 4。** 于是：

| 情形 | 单帧 | 200 帧合计 |
| --- | --- | --- |
| 12MP（4000×3000）原画质 | 33 MB | **6.6 GB** |
| 长边 2000 | 8 MB | 1.6 GB |
| 长边 1280 | 3.3 MB | 0.65 GB |
| 长边 960 | 1.8 MB | 0.37 GB |

**6.6 GB 没有任何消费级 GPU 装得下。** 所以"200 帧 + 原画质 + 全部同时驻留"
三者不可能同时成立，程序的做法是**让你明确选一个**，而不是背着你压：

| 选项 | 行为 |
| --- | --- |
| **自动适配**（默认） | 按「预算 ÷ 帧数」解出一个长边，保证**全部帧都装得下**。例如 200 帧 3:2 的图、预算 2 GB → 长边自动取 **2006 px**。状态栏会写出实际用的尺寸。 |
| **原画质不缩放** | 一个像素都不动。帧数多时会撞上预算，程序**载入到装不下为止并如实报告**装到第几帧、还差多少，然后建议你改成分辨率选项或分两批做。 |
| **长边 1920 / 1280 / 960** | 固定长边，自己掌握。 |

自动长边的算法就一行：`L ≤ sqrt(预算 × 长宽比 / (4 × 帧数))`，
所以帧数翻四倍、长边减半。这条公式在自检里被单独验证过。

**其他相关数字**：默认预算 2 GB，并会按 `navigator.deviceMemory` 向上放宽到 3–4 GB；
帧数上限 600（200 张不会被抽稀）；单帧长边硬上限 8192，同时受本机 GPU 的
`MAX_TEXTURE_SIZE` 约束。

### 纹理上传是"先近后远、最终补齐"

每帧的纹理是按需上传的：先传当前帧及其邻居（保证一打开就有画可看），
剩下的由**后台渐进循环**补齐，并且随着你拖帧滑块不断重新排序 —— 始终优先保证
"当前看得到的那些帧"是齐的。状态栏的「已上传 N/M 帧」就是这个进度。

**这一步不能省。** 没上传的帧拿不到纹理，而 WebGL 对"采样器没有纹理"的返回是
**未定义的**，多数驱动给纯白 —— 于是故障表现成"一块正常的白"，从画面上根本看不出来。
自检里为此加了两条：

- 渲染前**故意把纹理全部解绑**，断言每次帧平面绘制之前都重新绑定了真实纹理；
- 载入 40 帧，等后台循环跑完，断言 **40/40 都有纹理、0 帧失败**。

另外着色器里加了 `uHasTex`：万一某帧真的没有纹理，它会画成**品红**而不是白。
看见品红就是"纹理没上传"，看见白才是"照片内容就是白的" —— 这两种情况必须能区分。

**"原画质"的边界现在说得更准确了**：不选缩放时，程序确实一个像素都不动；
但它**不会**假装 200 帧 12MP 能装得下 —— 装不下就明说，把选择权交回给你。

### 原画质：做到了什么

1. 解码走 `createImageBitmap(file, …)`。**只有在你选了缩放时**才额外传
   `resizeWidth/resizeHeight`；选「原画质不缩放」时这两个参数根本不出现。
2. 纹理上传用 `texImage2D(…, 原始位图)`，不生成 mipmap，最小/放大过滤同值。
3. 点云颜色直接拷贝原图字节，不做降采样、不做加权平均。
4. 关闭抗锯齿、关闭色调映射、不做任何色彩空间变换。
5. 缩放失败时**退回原尺寸**，绝不静默丢帧。

### 输出

`导出当前视图 PNG`，以及 `?selftest` 之类的 URL 参数（见下）。

## 原画质：做到了什么、边界在哪

**做到的部分**

1. 解码只走 `createImageBitmap(file, …)`，**不传任何 resize 参数** —— 不经过 canvas 缩放、
   不经过任何有损编码。
2. 纹理上传用 `texImage2D(…, RGBA, RGBA, UNSIGNED_BYTE, 原始位图)`，不生成 mipmap，
   最小/放大过滤同值，像素值原样进显存。
3. 点云的颜色直接拷贝原图字节，不做降采样、不做加权平均。
4. 关闭抗锯齿、关闭色调映射、不做任何色彩空间变换。

**硬边界（必须如实说）**

- **GPU 单张纹理上限**（通常是 8192×8192 或 16384×16384）。超过这个尺寸的图会被
  **明确跳过并写出原因**，程序绝不会偷偷替你做压缩。上限值在状态栏里显示。
- **显存总量**：每帧纹理是 `宽 × 高 × 4` 字节，所以 20 张 6000×4000 的照片约 1.9 GB。
  超过预算（默认 2 GB，按 `navigator.deviceMemory` 放宽到 3–4 GB）时会停止载入并说明
  "已用多少、这一帧还需要多少"。帧数上限 600，超出按等间隔抽稀（保证整段时间跨度不丢），
  也会告诉你抽掉了多少帧。
- **旋转与 EXIF Orientation**：交给浏览器的解码器处理（它默认会应用方向标记）。
- **GIF / 动图**只取第一帧。
- **长宽比不一致**的照片不会被拉伸，会在统一的显示区域内居中留边。
- 为避免明显变形，所有帧按**第一帧的长宽比**排布。

**`test/view.test.mjs`（159 项）** —— 数学、相机、解算、排序、边界像素、轮廓判据、切割选区、EXIF。
这些不是"跑一遍没报错"，而是逐值断言：

- 矩阵语义（`mul(A,B)` = 先 B 后 A）、透视投影把近/远裁剪面映射到 NDC ∓1；
- **正视时相机在 +Z 轴上、世界原点恰好落在画布中心**（这条就是"正面对准第一帧"）；
- **第一帧的相机空间深度 < 最后一帧**（这条就是"正面=第一帧、背面=最后一帧"）；
- 照片右侧的点投到画面右半边、上方的点投到上半边（排除纹理左右镜像与上下翻转）；
- 立方体在 6 种极端窗口比例下都**完整入画**、不被裁切；
- 帧滑块 / 全部半透明 / 不透明度 0 / 点云四种状态下逐帧的不透明度与角色判定；
- 深度排序在正视与背视下的次序**正好相反**（由远到近）；
- 点云网格 `floor((w−1)/s)+1` 的列数行数、步长与预算的关系；
- 边界像素打包：**每条边逐列核对取到的是哪个像素、颜色是完整 RGB**
  （旧版这里断言的是"四条边压进 RGBA 四个通道"，那实际上把一个错的设计验证成了对的）；
- **侧立面的几何表**：左右墙沿 y、半长 = halfH、偏移 = ±halfW；上下墙沿 x、半长 = halfW、
  偏移 = ±halfH。**半长与偏移必须分开** —— 混用会让侧立面比照片高出 (halfW−halfH)；
- 沿边的纹理坐标方向（左右墙要上下翻转）、帧行坐标落在纹素中心且不越界；
- **轮廓判据**（`outlineContrast` / `outlineMask`）：在一张刻意构造的 8×8 图上，
  平色内部必须是 0、红↔绿（**亮度相同的强对比**）边界必须是 1.000、
  红↔深蓝是 0.961、只差 55/255 的弱边界是 0.216，且门槛 0.1 / 0.25 / 0.7
  对应的线条数是严格递减的（36 → 26 → 19）—— 也就是说"弱边界是被门槛滤掉的，
  不是算不出来"。整张纯色图必须提不出任何轮廓；
- **切割选区**：像素矩形 ↔ 归一化 uv 往返一致、反向拖出来的矩形被规整成正的、
  越界被夹到 `[0,1]`、面积算得对；**逐像素核对** 320×240 的图上"左上半区"的
  19200 个像素全部判为"在选区内"、其余 57600 个全部判为"在外面"；
  零面积选区被撑到至少 1 像素；同一块区域在 320×240 与 640×480 上得到同一个归一化选区；
- **框选编辑器**（纯函数层）：手柄命中（四角/四边/内部/外部）、整体平移被夹在画面内、
  拖某条边只改那一条边、拖过头会翻正而不是变成负面积；
  "整个画面"时按哪里都是画新矩形（否则用户拖着毫无反应）；
- **★ 点云与照片的朝向必须是同一套**：`pixelLocal` 让图像第 0 行落在 +y、第 0 列落在 −x；
  同一个图像像素经"照片路径"与"点云路径"投影后必须落在**同一个屏幕像素**
  （实测最大偏差 0.00 px）；并且有一条**反证**：把 y 写成 `v−0.5`（旧写法）会偏出 102 px；
- EXIF 解析：自己拼了一个带 APP1 的最小 JPEG，核对日期字段、Orientation、
  以及 `0000:00:00` 这种非法日期会被丢弃；
- 排序：文件名自然序（`frame_2` 在 `frame_10` 之前）、EXIF 优先、无 EXIF 时退化；
- 超纹理上限 / 超显存预算时**明确报错而不是降质**。

**`test/video.test.mjs`（79 项）** —— 视频抽帧。真解码器用不了（沙箱起不了浏览器），
所以用 `tools/harness.mjs` 里的 **`<video>` 替身**：它按 fps 把虚拟时间轴走一遍，
并且**只通过 `requestVideoFrameCallback` 报帧** —— 与真浏览器一致，
所以"每一帧都保留"这条是被真正断言的，而不是"我觉得它抓到了"：

- 抽到的帧数 = `时长 × 帧率`（一帧不少），时间戳按 `1/fps` 递增（无重复、无跳帧）；
- `longEdge = 0` 保持原始尺寸，给了长边就等比缩小（不拉伸）；
- **默认 `keepEvery = 1`**；显式选 3 时保留数 ≈ 呈现数/3，且步长如实上报；
- 帧率探测不建位图，`fps = 1 / 相邻帧时间差的中间值`（用"帧数/总时长"会被丢帧拉低）；
- **取消**：跑到 20 帧时置位就立刻停，不会把整段跑完；
- **上限**：`limit = 50` 就停在 50，并标记 `stoppedEarly`；
- **丢帧如实上报**：替身报 30 个丢帧，就绝不说"全抓到了"；
- 接进序列后：显存账 = 帧数×宽×高×4；`视频 + 照片` 混排时视频块内部保持时间顺序；
- **自动适配**：估算 600 帧 → 长边 222 → 63.5MB/64MB 预算，**600 帧一帧不少**；
- 装不下时**停下来并给出出路**（该每 2 帧取 1、或该降到什么分辨率），绝不静默丢帧；
- 视频源坏掉时报错并带上文件名，而不是给一个空序列。

> **★ 提示条的时间行为也在这里测**（用真时钟，这一节会真的花掉约 3.5 秒）：
> 载入一个必然丢帧的视频后，`#fatal` 立刻可见且**没有** `out` 类；2.4 秒时仍在；

> **★ 拷贝跟不上时的两条（针对实测丢 70% 帧那个故障）**
>

> 60/60 帧一帧不少、**`missed === 0`**（missed = 呈现了却没登记回调的帧，这正是旧写法的病根）、

### 这套验证抓到过的真 bug（说明它确实在干活）

1. **投影辅助函数少做透视除法** —— 立方体在数值上"超出画面"，而 GPU 自己会做除法所以
   肉眼看不出来。这条也是"立方体是否完整入画"的判据，错了就会误判。
2. **取景距离公式写错** —— 把横向与纵向的约束取了 max 之后再减深度，
   等于把横向余量错误地折算了纵向，斜看时立方体在竖直方向顶出画面。
3. **坐标系原点错开半个深度** —— 帧摆在 `z ∈ [0, depth]`，而立方体外框与取景按原点
   为中心的盒子算，两者错开 `depth/2`，画面被裁掉一块。
4. **点云步长量纲错** —— `sqrt(像素数 × 帧数 / 预算)` 被写成
   `sqrt(像素数 / (预算 × 帧数))`，200 帧 4K 时步长算成 2，实际需要 347。

**朝向类错误（参考渲染抓到的，最隐蔽的一类：画面里"有东西"、中心像素甚至也对得上）**

5. **帧平面水平镜像** —— `shaders.V_QUAD` 的 uv 相对顶点位置是左右反的
   （最左顶点的 `u=1`）。修正前，正视图看到的会是水平镜像的画面。
6. **点云上下翻转** —— `POINT_VS` 里对采样坐标取了负号（`-aPosPx.y`），
   而颜色纹理同样开了 `flipY`，于是点云整体上下颠倒。
   **这两处方向相反，所以只看平面或只看点云都发现不了**，必须拿已知位置的图形去核对。

> 这一类错误的教训：我前后三次手抄同一份 uv 数组，三次都抄错，而每次的表现都只是
> "某个已知位置的图形取到了背景色"。最后改成**从 `shaders.V_QUAD` 派生**
> （`quadLayout()`），从根上消除了抄错的可能。
> 另外，"四个候选 uv 数组谁与期望采样的吻合率最高"（99.8% vs 91%）
> 这种**定量判据**，比"我觉得它在三角形里"可靠得多。

**7. 点云着色器的 `int` uniform 精度不一致（链接期直接失败，用户实测报出）**

用户实际打开时报的是：

```
着色器编译/链接失败，画面不会正常显示。
[link:point] Precisions of uniform 'uSquare' differ between VERTEX and FRAGMENT shaders.
```

根因是 GLSL ES 的一个不直观规则：**顶点阶段给 `int` 默认 `highp`，而片元阶段
没有 `int` 的默认精度**。于是同一个 `uniform int uSquare` 在两侧精度不同，链接失败。
修复是在 `POINT_FS` 里显式写 `precision highp int;`。

**这个 bug 是我这一轮的验证网自己漏掉的**，原因很具体：我写了 uniform 静态审查，
但**只查了名字有没有被代码设置，没查类型与精度**。所以这一轮同时做了两件事：

- 把审查加强为「跨着色器共享的 uniform，类型与精度必须一致」（pipeline 套件 +4 项）；
- 按 README 里自己写的规矩做**反向验证**（`tools/verify-audit.mjs`）：
  把 `precision highp int;` 删掉，确认新审查真的会报出
  `uSquare: 顶点 highp int vs 片元 mediump int` —— 否则这条检查就是假阴性、等于没查。

这件事也印证了本文档开头那句：**静态检查能覆盖的只有"编译期就能发现的错误"，
而"真实驱动到底接不接受"只有真实浏览器说了算。** 第 5、6、7 号 bug 全都属于
"我的检查没覆盖到、但真实环境立刻暴露"的类型。

**8. 整个交互层被渲染层的异常拖垮（用户实测：拖入开出上百个标签页、点按钮没反应）**

用户报的是两个现象，其实是同一个根因：

- 拖入一批照片 → 浏览器把每张照片当链接打开，**一次开出上百个标签页**；
- 点「打开照片」→ **毫无反应**。

`boot()` 原来的顺序是「WebGL 初始化 → `bindUI()` → `resize()`」。
渲染层任何一行抛异常，`bindUI()` 就整个不执行 —— 拖放监听不存在，
浏览器于是执行拖放的**默认行为**（打开文件）；选文件的绑定也不存在，所以点了没反应。
**一个渲染层的小问题，把整个交互层一起拖垮了。**

修复分三层，每一层都是"让失败不可能静默发生"：

1. **拖放拦截提到脚本求值阶段**（`armDragGuard()`，在 `boot()` 之前就注册），
   并且改用 **`document` + 捕获阶段**。这样即使 `boot()` 整个失败，拖放照样被拦下。
2. **选文件改成不依赖 JS**：原来是 `<label for>` + 隐藏 `<input hidden>`，
   现在是一个**透明 input 铺满整个按钮**——用户点到的就是 `<input type="file">` 本身，
   浏览器原生打开对话框。脚本全挂了这条路也通。
3. **`boot()` 重排为「先输入、后渲染」**，每一步各自 `try` 住，
   渲染层出问题只报渲染层的错，绝不再牵连交互。

顺带补上的两个附带 bug：

- **桩里缺 `deleteBuffer`** —— 说明"再拖入一批新照片"的释放路径从来没被测过。
  真浏览器有这个 API 所以不会报错，但这意味着该路径一直是未验证状态。
- 输入通路测试原本插在状态一致性检查之前，会把序列换成 2 帧，
  让"恰好一个不透明帧"的断言前提失效 —— 已调整顺序并在注释里写明原因。

**这一轮也让我犯了一个低级错误，值得记下来**：我用 PowerShell 的
`Get-Content` / `Set-Content` 去删一段代码，把文件里的中文全部写成了乱码
（Windows PowerShell 5.1 默认按 ANSI 码页读写），而这个目录没有 git，无法回滚，
只能整份重写。**改文本文件一律用编辑工具，不要用 shell 命令绕。**

**9. 200 帧的白色描边把画面叠成一片纯白（用户实测："加载出来的立方体所有切面都是纯白色"）**

我一开始往"纹理没上传 → 采样默认白纹理"那边查（这条也确实是个真问题，见上面"纹理上传"
一节）。但用户自己找到了真正的触发条件：**打开"白色线框"就会让画面变成纯白。**

原因很直接：那个开关原本是"给每一帧的显示区域描一个白框"。200 帧就是 200 个白框，
每个都写深度、都以白色混合 —— 叠起来就是整片白。而且它**默认是开的**。

修复是两件事：

1. 把"立方体线框"和"每帧显示区域描边"拆成两个独立开关：
   前者是**立方体本身的 12 条棱**（`GL_LINES`，24 个顶点），后者的默认值改为**关闭**；
2. 完全透明的帧连侧墙一起跳过 —— 顺带修掉了一个相关的逻辑漏洞：
   原先的跳过条件是 `if (opacity ≤ 0 && !showFrameOutline) continue`，
   于是**打开描边会连带把已经隐形的帧的侧墙"复活"**，画出一片完全不合逻辑的不透明墙。

回归网：pipeline 套件里断言线框是 24 个顶点的 `GL_LINES`、"描边默认不画"、
"打开描边时两档亮度"、"不透明度 0 时侧立面也不画"。

> **补记（第 11/12 轮发现的）**：这一轮我以为"每帧显示区域描边"是一条线框，
> 其实它当时是用 `TRIANGLE_STRIP` **填充**出来的一个四边形 —— 四个角缩到中心、
> 于是四条"从角到中心的线"围出来的正是整个矩形。也就是说它一直是**半透明白色蒙版**，
> 这才是"200 帧叠成纯白"的完整解释。现在它改成了真正的 8 顶点 `GL_LINES` 矩形线框。

**10. 点云一个像素都不显示：着色器声明了 `aPos` 却没用（用户实测："点云没有任何显示"）**

这个 bug 的性质和第 5、6 号一样：**画面"没有东西"，而不是"东西在错的地方"**，
所以只看"有没有画出内容"的断言根本抓不到。

真实的矛盾在两条指令之间：

```
drawArraysInstanced(gl.TRIANGLES, 0, 6, n)     // 每实例 6 个顶点（两个三角形拼一个方点）
```

而 `POINT_VS` 里：`layout(location=0) in vec3 aPos;` 声明了，**却从未被使用** ——
撑开方块用的是 `gl_PointSize`。`gl_PointSize` **只在 `gl.POINTS` 下有效**；
在 `gl.TRIANGLES` 下它被忽略，于是六个顶点全部落在同一个位置，
三角形退化成零面积，一个像素都画不出来。

修复是把方块在裁剪空间里撑开：

```glsl
vec4 clip = uProj * uView * uModel * vec4(aPosPx, 0.0, 1.0);
float size = ...;                                  // 单位：屏幕像素
vec2 perPixel = 2.0 / max(uViewport, vec2(1.0));   // 一个像素在 NDC 里有多宽
clip.xy += aPos.xy * 0.5 * size * perPixel * clip.w;   // clip.w 兼顾正交与透视
gl_Position = clip;
```

圆点模式也随之改：原来用 `gl_PointCoord`（同样只属于 `gl.POINTS`），
现在用一个 `vLocal` varying（就是 `aPos.xy * 0.5`）在片元里 `length()` 切圆。

**这次我改了验证方式**：不再只断言"发出了实例化绘制"（那一直都是对的），
而是断言**两个事实之间的关系**：

> 图元是 `TRIANGLES` ⇒ 顶点着色器必须自己把方块撑开，且不得出现 `gl_PointSize` / `gl_PointCoord`。

这类"两个组件必须互相匹配"的不变量，才是能抓住这个 bug 的东西。
顺手也把"顶点着色器公式算出来正好是 size 像素"做了数值核对。

> 另一个附带的坑：即使点云画出来了，**正视图下当前帧是不透明的，它会把后面所有帧的点按深度
> 遮挡掉** —— 那是正确的深度行为，不是 bug。想看完整的点云，用`等轴`视角，
> 或把`当前帧`的不透明度调低 / 打开`全部半透明`。

**11. 侧面全是灰色、而且每一帧颜色都一样（用户实测："给侧面加的厚度颜色全是灰色"）**

这一个故障背后是**四个错误叠在一起**，任何单独一个都足以让侧面不对：

1. 边界像素图集把四条边挤进 RGBA 四个通道，每个通道只存一个**R 分量** ——
   于是侧面在数据层面就只能是灰的（代码注释里甚至写着"只够画灰度的色带"，
   等于把一个错误设计当成了前提）。
2. 渲染时算出的是 `W × n`（宽 × 帧数）的像素，上传却写成了
   `texImage2D(…, width, 1, …)` —— **高度写死 1，n−1 帧的数据被静默丢掉**，
   一个错误都不报。于是所有帧只能取到第 0 帧的颜色。
3. 片元着色器用 `max(max(r,g), max(b,a))` 取一个标量当灰度输出 ——
   四个面因此完全一样。
4. 几何上只用一个 `uLong` 同时当"沿边半长"和"固定轴偏移"，于是**左右墙的半长被写成了
   halfW**（正确值是 halfH），侧立面比照片高出 `halfW − halfH`；上下墙又比照片窄。
   用户说的"**加出来的厚度尺寸也不对**"就是这一条。

修复：每条边一张**独立的、边长 × 帧数**的纹理，纹素是**完整 RGBA**；
着色器直接输出 `c.rgb`；几何表拆成 `uSpan` / `uOff` / `uAxisY` 三个量，
并抽到 `STC.view.bandSides()` 里让渲染器与参考渲染共用。

**最该记的是验证为什么没抓住它。** 两个原因：

- pipeline 套件当时断言的恰恰是错的行为：`侧面颜色条图集是 1 像素高的带状纹理`
  （那就是被截断的那张）、`侧面颜色条仍是 4 条`。**断言贴着实现写，就把 bug 写成了规格。**
- REF 套件的参考光栅器用的是一套**完全不同的模型**（一条带子从 z=0 拉到 depth、
  按帧号插值、直接用 `edgeColors` 取真实 RGB），所以它一路上都是绿的，
  而真实渲染提交的却是"每帧一片薄片 + 灰度 max"。**参考实现与被验证的实现不是同一件事，
  验证就是空的。**

这一轮把两件事都改了：

- 桩里加了**尺寸/数据长度一致性检查**（`texImage2D` 声明 `w×h` 就必须正好 `w×h×4` 字节），
  真 WebGL 会静默截断的地方，桩里直接记违规；
- 参考渲染改成与渲染器**共用同一批纯函数**（`bandSides` / `edgeCoord` / `frameRow` / `packEdge`），
  并新增"每帧侧立面必须是那一帧自己的颜色"的逐帧探针断言。

**12. 白色线框完全不显示：把 Buffer 当成了 VAO（用户实测）**

```js
geom.cage = ctx.buffer(new Float32Array(cageVerts()));   // 这是个 Buffer
...
gl.bindVertexArray(geom.cage);                            // 却当成 VAO 绑定
gl.drawArrays(gl.LINES, 0, 24);
```

`bindVertexArray` 收到一个 `WebGLBuffer` 时，真 WebGL2 会报 `INVALID_OPERATION`
并且**保留原来绑定的 VAO** —— 于是这次 `drawArrays` 画的是别的几何，或者什么都没有。
时间轴（`geom.axis`）是同一个写法，所以**两者都一次都没画出来过**。

雪上加霜的是第二层原因：即使 VAO 是对的，标记那一段当时**没有关深度测试**，
外框会被立方体自己的不透明面挡住 —— 用户看到的仍然是"没有线框"。

修复：外框与时间轴各自建**真正的 VAO**（`ctx.vao` + `ctx.attrib`），
画标记之前 `disable(DEPTH_TEST)`、画完再 `enable`，并把立方体外框的颜色改成**白色**。

回归网：桩里记录每一次 `bindVertexArray` 收到的对象类别，
断言"渲染全程没有把 Buffer 当 VAO 绑定"；并断言外框 24 顶点、时间轴 2 顶点都真的发出绘制。

> 这两个 bug（10/11/12）有个共同点：**我的桩只"记录"、不"校验"**。
> 它忠实地记下了"绑了一个 Buffer""上传了一张 W×1 的纹理"，
> 但没有任何一条断言去问"这在真 WebGL 里合法吗"。
> 现在的做法是：桩对**协议级违规**（类型不对、长度不符）主动记违规，测试里断言违规数为 0。

**13. 厚度条：不透明度不跟着走、没有总开关、以及那根让人误会的黄线（用户实测三条）**

这一轮的三条反馈里，前两条是**真的设计漏洞**，第三条是**表达不清**：

1. **"厚度条不透明度不会改变"** —— 对。立面的 `uOpacity` 当时恒为 1：
   把「其他帧」拉到 0，照片没了、边还在，整圈边像一个不透明外壳。
   修复：立面的不透明度**就是那一帧照片的不透明度**，并且按帧平面同一套规则分批绘制
   （不透明的一批写深度，半透明的一批不写深度、由远到近排）。
2. **"需要一个打开/关闭厚度条的开关"** —— 对。以前只有一个"侧面颜色条：
   边界像素 / 平均色 / 关闭"的三选一，语义上不像是总开关。
   现在面板里是「**显示厚度条**」复选框（关掉时连四张图集纹理一起释放），
   旁边只留「边界像素 / 平均色」两种取色方式。
3. **"为什么会有一根黄色的线指示正面？"** —— 那是**时间轴**：从第一帧中心指向最后一帧中心。
   它表达的是"时间往哪边走"，但因为（a）两端长得一样、没有箭头，
   （b）标记这一轮改成不被遮挡之后它会穿过立方体显示，
   于是就很容易被读成"一根指着正面的线"。修复：给它加了**四根刺组成的箭头**
   （主线 2 + 箭头 8 = 10 个顶点），箭头指向**最后一帧**；不想要可以用「时间轴」复选框关掉。

**关于"厚度条只有上表面，另外三个侧面都没有"**：这一条我没有能找到"少画了面"的证据 ——
四色诊断模式下四个面都在画（48 次绘制、四张不同的纹理），参考渲染器在等轴视角下
四个面各贡献约 1.3～1.5 万像素。所以我在文档和面板里把**可见性**这条讲清楚了：

- 正视：四个立面全都正对相机，投影退化成零宽 —— **一个都看不见**（几何必然）；
- 等轴：最多看到两个（正对相机的两个），另外两个被立方体自己挡住（正确遮挡）；
- 俯视：只看得到上、下。

而立面的颜色来自**用户自己照片的边缘**：风景照上边是亮的天空、左右和下边是暗的地面，
于是深色的立面压在近乎黑的背景上就"看不见" —— 看起来就像只有上表面被生成了。
为此加了「**诊断：四色立面**」：把四个面分别涂成红/绿/蓝/黄，
一眼就能区分"没画出来"和"画出来了但颜色与背景一样"。

**14. 新 uniform 名把自检桩的 program 识别搞错（这一轮自己抓到的验证工具 bug）**

轮廓提取给 `PLANE_FS` 加了 `uEdgeThreshold`，而 `tools/harness.mjs` 里判断"这次
`drawArrays` 是谁画的"用的是正则 `/uEdge/` → band。于是**帧平面被认成了色带**：
pipeline 套件一口气报了 20 多条失败 —— "帧平面绘制次数 = 12 → 0 次"、
"每帧四周色带各画 4 条 → 60 条"（60 = 48 条真色带 + 12 个被误认的帧平面）。

修法是把判据换成 band **独有**的 `uEdgeTex`，并在注释里写清"不能用 `uEdge`"。
值得记下来的是：**这 20 多条失败里没有一条是产品代码的问题**，
如果当时按"失败了就去改渲染器"的思路走，就会把正确的渲染器改坏。
**先看一眼失败是不是集中在"归类"这种横切断言上，往往能立刻定位到工具本身。**

**15. 合成样本里的颜色回绕（读参考图时抓到的）**

为了核对轮廓参考图，我直接把 `07-front-frame0-outline.png` 的像素打出来看，
结果在底部的渐变条上发现一条**刺眼的亮红**。它不在照片的任何设计里 ——
根因在 `tools/make-sample.mjs`：渐变值是 `round(10 + 30·sin(…))`，最小会到 **−20**，
而目标是 `Uint8Array`，负值**回绕成 236**，于是在暗蓝渐变的中间凭空出现亮红像素。

这不影响程序，只影响测试夹具；但它说明一件事：**参考图不能只用眼睛扫一眼"看着对"**，
把可疑处的像素值打出来，才知道那是设计还是 bug。修法是 clamp 到 0。

**16. 点云与照片上下颠倒（做"切割"时顺着 uv 朝向查出来的）**

切割要用到"图像坐标 ↔ 帧平面 uv"的对应关系，于是我把两条路径摊开对照，发现
**同一个图像像素在两条路径上的局部 y 是相反的**：

```js
// 照片（帧平面）：v=0 给的是四边形上方顶点，而 v=0 是图像顶部
ly_plane = 0.5 - (z + 0.5) / h      // 图像顶行 → +y
// 点云（旧写法）：直接把行号当局部 y
ly_point = (z + 0.5) / h - 0.5      // 图像顶行 → −y   ← 反了
```

所以点云相对照片是**上下镜像**的。这个错误当年被"修"过一次（6 号 bug 说
`POINT_VS` 里的 `-aPosPx.y` 是罪魁祸首），但那次判断是在"flipY 让 v 翻转"这个
（写反了的）前提上做的，结果把正确的符号去掉了 —— **同一类错误不会因为改过一次就消失**。

这一轮的修法不是再改一次符号，而是**取消两条路径各写一套公式**：
位置改由 `STC.view.pixelLocal(w, h, x, z)` 统一烘焙，并补上一条"投影交叉核对"断言 ——
同一个图像像素经照片路径与点云路径投影后必须落在**同一个屏幕像素**，
再加一条反证（旧写法会偏出 102 px）。这样两边**不可能**再不一致。

**17. 桩里少了一个 id，让一半的界面静默失联（自检工具的问题，不是产品的问题）**

`tools/harness.mjs` 的 DOM 清单里漏了 `lumDir`。于是 `bindUI()` 在
`$('lumDir').addEventListener(...)` 那一行抛异常，被 `boot()` 的 try/catch 接住 ——
**后面所有控件的事件绑定全部没有注册**：方点、三档描边、立方体线框、时间轴、
视角切换、以及这一轮新加的切割。表现是"测试全绿"，但那几个开关其实从来没被点过。

发现它是因为新加的切割开关"点了没反应"。修法两条：

- 桩里补上 `lumDir`；
- 在 pipeline 套件里加一条**元检查**：`src/index.html` 里出现的每个 id，
  桩的 DOM 里都必须存在；并断言提示条里没有"界面事件绑定失败"。
  （注意方向：这条检查关心的是"桩有没有如实建模页面"，
  而不是"代码引用了页面里没有的 id" —— 后者只在有 `if ($('x'))` 保护时无害。）

**18. 框选的坐标用错了分母：选出来的区域整体偏左（用户实测）**

用户的原话是"实际效果是把框选区域重新挪到画面最左侧来显示"。根因在**布局**：

```css
.cbox{display:flex;flex-direction:column}      /* 面板 */
#cropWrap{display:inline-block}                /* 框选层：flex 子项 → 被拉伸到整个面板宽度 */
#cropCanvas{max-width:min(90vw,820px);max-height:62vh}   /* 画布：常常窄得多 */
```

框选层是 flex 列的子项，`align-items: stretch` 会把它拉满面板宽度；而画布同时受
`max-width` 与 **`max-height:62vh`** 限制 —— 竖构图照片或矮窗口下，画布只有外框的一半宽。
于是两个量都用错了分母：

- 鼠标坐标 → uv 用的是**外框**宽度 ⇒ uv 整体偏小（画面越窄偏得越多）；
- 选区框的百分比定位也用外框宽度 ⇒ **框正好落在鼠标下面，看起来完全正常**。

两者一起错，正好互相掩盖：面板里"框跟手"，3D 里却切到了左边那块。竖构图照片最明显 ——
框在中间，切出来的是靠左的一条。

修法（两条一起，缺一不可）：

- CSS：`#cropWrap{width:fit-content;height:fit-content}`，让框选层**收缩到画布大小**；
- JS：坐标换算与容差一律以 `#cropCanvas` 的矩形为准（`cropBox()`），选区框改用
  **px 定位**、锚在画布的真实位置上，不再依赖外层容器的尺寸。

回归网也是两条：桩里刻意让外层（800×400）比画布（400×300）宽一倍，
然后断言"从画布正中拖到右下角 = uv (0.5,0.5)~(1,1)"、以及选区框的 px 位置
（`left=140 top=85 w=200 h=150`）。按旧写法这两条会得到 0.125~0.375 和错位的框。

> 这一条的教训：**"看起来对"和"算得对"是两件事**。面板里的框跟着鼠标走，
> 并不能证明换算是对的 —— 只要框的位置和换算用了同一个错误的分母，视觉反馈就是自洽的。
> 所以坐标换算必须以**真正显示图像的那个元素**为基准，并且用"已知点 → 已知 uv"去断言。

### 你应该自己确认的部分（以及怎么确认）**最重要的三条是第 2、6、7 条** —— 它们正好覆盖无浏览器环境下最难自查的三类错误
（正面朝向、点云朝向、点云是否看得见）。这一轮新增的是 **8（红字 3 秒渐隐）**、
**10（轮廓提取）** 和 **11（切割）**。第 6 条尤其要看：这一轮把它回归网的强度补上了
（照片与点云现在共用同一条朝向公式，见 16 号 bug）。

1. 打开 `index.html`，画面里能看到一个立体方盒（等轴视角），不是黑屏或白屏。
   也可以先打开 `test/reference/06-front-frame12-ghosts.png`，那是同一状态下的**参考图**，
   对照着看更省事。
2. **正面朝向**：点 `正视`，正面应该正好是第一帧、背面是最后一帧。
   最容易看出的判据是**原图里的文字方向**：如果正视图里照片是左右镜像的，就是 5 号 bug 复发。
3. 拖 `当前帧` 滑块：被选中的那一帧应该"实起来"，其余帧保持半透明。
4. 把 `其他帧` 拉到 0：内容（含厚度条）消失，只剩**白色线框**与**橙色时间轴箭头**
   （箭头指着最后一帧）。
   然后勾上 `每张照片的显示区域描边`，应该能看到每帧一个白色矩形线框 ——
   这是 9 号 bug 那个开关，帧数多的时候它会明显糊成一片白，那是预期行为。
5. **厚度条**：用`等轴`视角、两个不透明度都拉到 1，斜看立方体 ——
   应该能看到上（或下）和左（或右）两个侧面，每个面都是一层层**彩色**的薄片边，
   颜色来自那张照片最外一列/一行的真实像素，而且**每层颜色不同**。
   - 如果只有上表面、左右看着是空的：先勾上「**诊断：四色立面**」。
     四个面变成红/绿/蓝/黄就说明**四个面都在画**，之前只是"深色边压在深色背景上"；
     如果四色模式下仍然缺面，那才是真的渲染问题，请截图告诉我缺哪个颜色。
   - 把 `帧厚度` 拖大，立面会明显变宽（标签会显示 ≈多少原屏幕像素、占帧距的百分比）。
   - 把 `其他帧` 从 1 往 0 拖：它们的边应该跟照片一起淡下去（这是这一轮修掉的）。
   - 「显示厚度条」关掉后，整个立方体只剩照片与线框。
   - 注意**正视时看不到任何立面**（侧立面全都正对相机、投影退化），这是几何必然。
6. **点云朝向**：切到 `点云`。非当前帧变成散点，**上下方向必须与照片一致**；
   找一个明显不对称的景物（天空/地面、天花板/地板），如果上下颠倒了，就是 6 号 bug 复发。
7. **点云是否看得见**（10 号 bug 的验收）：切到 `点云` 后**画面里必须真的出现点**。
   - 用 `等轴` 视角看，别用正视：正视时当前帧是不透明的，会把后面帧的点按深度遮掉；
   - 把 `点大小` 拉到 6~8 更容易看清；
   - 拖 `密度幂次` 与 `门槛`：密度应该明显变化；切 `亮处更密` / `暗处更密`，
     密集的区域应该在明暗之间明显换边；
   - 状态栏的「已上传 N/M 帧」如果长期不齐，点云只会有一部分帧 —— 那是上传进度，不是 bug。
8. 页面若弹红字，把它连同状态栏文字一起反馈 —— 页面会自己把着色器编译日志、
   运行时错误直接显示在画面上，不用翻 F12 控制台。
   **红字会在 3 秒后自己淡出**（丢帧那类提示必然出现，不该一直挡着画面）；
   想再看一次就点它一下，完整文本也在鼠标悬停的 `title` 里。淡出**不代表**问题消失了。
9. **视频**：拖一段短视频进去（十来秒即可），应该看到：
   - 进度条显示「正在抽取视频帧 … 已抓 N 帧（呈现 M 帧）　X 帧/秒　约还需 Y 秒」，
     **M 会随播放增长**；如果拷贝跟不上，还会显示「跟不上，已降到 0.25× 速度（保帧优先）」；
   - 载入后状态栏写着「视频 xxx.mp4：N.N 秒 → K 帧（呈现 K 帧）」——
     **K 应该等于 时长 × 帧率**（30fps 的 10 秒视频就是 300 帧）；
   - 拖动帧滑块，画面是连续的动作（每一帧都在，没有跳）；
   - 如果提示里出现"解码器仍报了 X 个丢帧"，请**把「分辨率」调低**（例如 1280 或 960）
     再试一次 —— 那时丢帧应该变成 0。**不要**改用「每 N 帧取 1」，那只是少抽样。
10. **轮廓提取**：勾上「**只保留轮廓（颜色分界线）**」，画面里的平坦区域应该**消失**，
    只剩物体的边缘线，线宽看起来差不多是**一个像素**。
    - 找一个**红↔绿**这种"亮度几乎一样但颜色差很大"的边界：它**必须**被留出来。
      如果这类等亮度边界整片消失，说明判据退化成亮度差了（这正是这一轮刻意避开的坑）。
    - 拖「对比门槛」：往小拖，更多的弱边界出现（包括照片的噪点、渐变的台阶）；
      往大拖，只剩最硬的边界。
    - 照片缩得很小时线不该消失、放得很大时不该整片变成噪点 ——
      这两种病分别对应"线宽没跟着屏幕走"和"采样步长小于一个纹素"。
    - 关掉开关，画面必须**立刻**恢复成完整照片（它不是破坏性处理）。
11. **切割**：点「框选区域…」，在当前帧上拖一个矩形（比如只框住画面里某个人/某个路牌），
    点「应用这个选区」。应该看到：
    - **框住哪块，留下的就是哪块，位置不变** —— 如果留下的区域明显偏左（或者偏上/偏下），
      说明坐标换算又用错了分母（见 18 号 bug）。**竖构图照片最容易暴露这个问题**，
      请专门拿一张竖向照片试一次；
    - 立方体里**每一帧**都只剩那块区域，其余部分露背景 —— 选区是对所有帧生效的，
      不是只切当前那一张（这是最容易误解的一点）；
    - 框选面板里选区外是压暗的，用「整个画面」怎么框都是画新矩形（整幅选区无处可移）；
    - 拖选区内部能整体移动、拖四角/四边能缩放、拖过头会翻正、「取消」不会改动原选区；
    - **切到「点云」模式，选区必须照样生效**（选区外的点不画）；
    - 把「其他帧」拉到 1.0 变成实心立方体：每一层都被切出同一块区域，边缘对齐；
    - **侧面厚度条不参与切割**（它仍是整张照片的边）；开着「显示区域描边」时，
      那个白框会跟着选区走，可以拿它核对"选区的边界到底在哪"；
    - 勾掉开关 → 立刻恢复完整画面，**再勾上** → 之前的选区还在（不用重新框）。

### 为什么源码是分开的、交付物却是单文件

单文件是为了"双击就能开、离线、不依赖任何东西"；但把所有逻辑塞进一个文件里没法维护。
所以 `build.mjs` 负责把 `src/` 合成 `index.html`。**改功能请改 `src/`，然后跑一次构建：**

```
node build.mjs
```

构建时会顺带做两项检查：每个模块单独能否解析、以及**拼起来之后整体能否解析**
（后者专门用来抓"某个模块的 IIFE 调用没写完整、导致后面所有代码掉进它的作用域"这类问题）。

### 关于 `?demo=`、`?hold=1`、`?banddebug=1`

`?demo=<路径模版>&n=<帧数>` 直接加载一组 URL 作为序列，例如
`?demo=./sample/frame_%03d.png&n=24`；`?hold=1` 关掉任何自动动画，方便复现固定状态；
`?banddebug=1` 把四个侧立面涂成红/绿/蓝/黄（等价于面板里的「诊断：四色立面」），
`?bands=0` 直接以关闭厚度条的状态启动。这几个参数是给自检和排查用的，日常使用不需要。

## 已知取舍

- **视频抽帧按"拷贝速度"推进，不一定实时**：拷贝跟得上就接近实时；
  跟不上会自动降速到 0.25× 甚至暂停（**保帧优先**），所以总耗时可能超过视频时长。
  进度条上有"帧/秒"和"约还需几秒"。之所以不用"按间隔 seek"来加速，
  是因为那样抽出来的时间点既不均匀也不等于真实帧时刻。
- **视频的帧数上限是 2000 帧**（照片是 600 帧，超过会等间隔抽稀；视频**不抽稀**，
  到上限就停下来并告诉用户"该每几帧取 1"）。真正卡住的是显存预算。
  **想解决丢帧请调低分辨率，不要用抽稀** —— 抽稀只是少抽样，丢掉的帧并不会回来。
- **点云密度是自动的**：为了保证流畅，总点数被限制在 400 万。超大图会看到点变稀
  （状态栏会显示实际点数）。这是"能转得动"与"点够密"之间的折中，不是压缩：每个点的颜色
  仍然是原始像素值。密度还会再按亮度加权剥掉一部分点（这是特性，不是降质）。
- **切割目前只有矩形**，没有多边形/套索：选区是"一张图上的一个矩形"，对所有帧生效。
  需要不规则形状时，可以先在图片编辑器里裁好再导进来。
- **切割只切"影像"，不切"外壳"**：每帧薄片的四个立面（厚度条）仍然是整张照片最外一列/一行的颜色。
  这与"只显示选区内的影像"是一致的 —— 立面表达的是"这张照片有厚度"，
  而不是"照片被裁过"。
- **多个帧的纹理是惰性上传的**：先上传当前帧及其邻居，再向两侧扩散。
  大序列在刚开始的几百毫秒里可能有些帧还是空的，随后补齐。
  **点云缓冲也是惰性的**：切到点云时会为每一帧建缓冲，200 帧的大序列需要等一会儿
  （有进度提示）。
- **帧厚度是"照片宽度的百分比"**：默认 0.02，面板里同时换算成原图像素与帧距占比。
  200 帧时会被自动夹到帧间距的 90%，所以大序列的侧立面会明显更薄 —— 这是几何必然。
- **侧立面是"每帧一片"，不是一整面墙**：所以帧与帧之间会留一条 10% 的缝
  （厚度被夹在帧距的 90%）。这是"每张照片是一个有厚度的薄片"这个模型的必然结果：
  想要完全无缝，把厚度调到被夹住的上限即可，缝会小到看不见。
- **不同长宽比的帧会被拉伸**（所有帧共用同一个平面尺寸，取第一帧的宽高比）。
  混排照片与视频时尽量用同一种画幅。
- 未做帧间对齐/稳像：如果拍摄时相机有移动，堆叠后背景会出现重影，需要先自己稳像。
